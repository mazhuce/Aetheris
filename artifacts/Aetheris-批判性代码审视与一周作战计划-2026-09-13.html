审视日期：2026-09-13
审视范围：整个 monorepo —— 10 个 Spring Boot 服务 + gateway + React 控制台 + 56 个 Flyway 迁移 + Docker Compose + CI
审视方法：源码逐行核查 + 命令行取证（git 跟踪状态、测试报告、依赖扫描、配置比对），每条结论都附带文件路径与行号

0. 一句话结论

这套系统的工程密度已经很高，但它的"交付成熟度"严重落后于"编码密度"——442 个测试全绿、11 个容器全部健康、56 个迁移整齐排布，然而它没有一次数据库备份、没有一个指标端点、没有一条跨服务 traceId、没有一个可安装升级的发布物。

换句话说：它现在是一个极优秀的作品，还不是一个能交付的产品。 下周的工作重点不该是"再加一个能力"，而是把已经写好的能力变成"敢让别人碰"的系统。

本次共定位 26 个问题：阻断级 3、高危 7、中危 11、低危 5。其中 3 个直接决定"能不能交给别人用"，7 个决定"出问题能不能查、能不能扛并发"。

2. 两处必须更正的事实（既有报告与代码不符）

在动手之前，先把两个已经被写进文档、但与代码事实不符的结论纠正掉——否则后续排期会建立在错误的基线上。

2.1 「110 个 Flyway 迁移」→ 实际源码是 56 个

artifacts/Aetheris-全项目审查报告.md 第 2.3 节统计为 110 个迁移。实测源码 services/*/src/main/resources/db/migration/ 下只有 56 个 V 前缀迁移；差额来自 target/classes/db/migration/ 下的构建副本被一并计入。迁移数量被高估了近一倍，这会影响"迁移健康度"的判断。

2.2 「前端权限是伪安全、可越权」→ 实测不构成越权

子调查给出了一条 P0 结论：前端把角色存在 localStorage（apps/web/src/utils/access.ts:5 的 getCurrentRole() 直接读 localStorage.getItem(ROLE_KEY)），用户改一行 DevTools 就能解锁 /admin/* 路由，因此是越权漏洞。

我复核后认为这个定性不准确，实测证据如下：

apps/gateway/src/main/java/com/aetheris/gateway/config/JwtAuthFilter.java:168-181：

ServerHttpRequest mutated = exchange.getRequest()
    .mutate()
    .headers(headers -> {
        headers.set("X-User-Name", username);
        headers.set("X-User-Role", authenticatedRole);   // ← 角色来自 JWT 声明，覆盖客户端传值
        headers.set(IdentitySigner.IDENTITY_HEADER, identitySignature);
    })

网关用 JWT 中的角色强制覆盖 X-User-Name / X-User-Role / X-User-Id，客户端伪造的这些头会被重写丢弃；写操作还要经 AuthPermissionGate → auth 的 /internal/permissions/may-mutate|may-manage 判定，auth 不可用时 fail-closed 返回 503；用户管理接口有服务端 AdminGuard.requireManage()（services/auth/.../AuthUserAdminController.java:152）。

所以：前端角色门禁确实只是"UI 收敛"，但不是安全漏洞——真正的边界在网关和 auth。 正确的表述是「纵深防御不完整」：metadata 有 IdentityVerifier 验签，而 auth、system、ai-agent 仍直接信任明文头（见 P2-1），一旦有内网直连路径就存在冒充空间。

保留一条真实结论：前端角色存 localStorage 且登出时未清理 react-query 缓存（TopNav.tsx:74-82），存在"切换账号后读到上一个账号缓存数据"的真实风险——这条要修。

4. 阻断级问题详解（B1–B3）

B1. 全平台零备份 —— 这是唯一"灭顶"级风险

证据：find . -iname "*backup*" -o -iname "*pg_dump*" -o -iname "*restore*" 在排除 node_modules 后结果为空。数据全部落在一个命名卷上：

# docker-compose.yml
services:
  postgres:
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:

影响：一次 docker compose down -v、一次卷损坏、一次勒索加密，10 个服务的全部业务数据、权限配置、审计日志、任务历史、语义资产一次性归零，且没有任何东西可以恢复。这不是"缺一个功能"，这是"整套系统押在一个卷上"。

还有一层叠加风险（M5）：56 个迁移没有任何 U 前缀回滚脚本，其中 2 个迁移带 DELETE FROM（V8__lineage_source.sql:19,34 直接删血缘数据）。升级失败时既不能回滚代码，也没有数据快照可退。

修法（详见 D1）：
1. pg_dump -Fc 定时全量 + WAL 归档，落到对象存储/异机；
2. 把卷换成绑定挂载或至少加独立备份卷；
3. 必须做一次"空环境恢复演练"——恢复不是"有备份文件"，而是"从零能跑起来"；
4. 破坏性迁移前强制快照，DELETE FROM 改为标记失效。

B2. 可观测性三缺 —— 出故障时只能靠猜

证据（三条命令全部返回 0）：

grep -rn "micrometer|prometheus" services/*/pom.xml apps/gateway/pom.xml  → 0 命中
grep -rn "traceId|MDC|OpenTelemetry" services apps/gateway                → 0 命中
find . -name "logback*.xml"                                               → 0 个
grep -c "max-size|logging:" docker-compose.yml                           → 0

各服务 application.yml 的 actuator 只暴露 health,info，没有 /actuator/prometheus。日志是默认 json-file 驱动且没有 max-size，长期运行会撑爆磁盘。

影响：这套系统有 11 个容器、跨服务 HTTP 调用链（网关→workflow→metadata→数据源，最长 5 跳）、有 Spark 远端执行、有 Quartz 集群调度——但一次慢查询无法从看板追到语义层再追到 SQL 和引擎，一次超时无法判断卡在哪一跳，一次 P95 劣化没有任何历史数据可比。项目本身有这个自觉（docs/enterprise-delivery-roadmap.md:90 把 R11 可观测列为必需项），但排在 11 次迭代之后——这个顺序是错的，可观测性应该是"现在就做"，因为后面所有修复都需要它来验证效果。

修法（详见 D2）：加 micrometer-registry-prometheus，暴露 /actuator/prometheus；filter 里生成 X-Request-Id 写入 MDC 并沿调用链透传；logback 统一 JSON 格式 + traceId 字段；compose 加 logging.options.max-size/max-file；起一个 Prometheus + Grafana。

B3. 弱默认密钥能通过启动校验

证据：.env.example 给出的"示例值"，长度恰好都越过启动校验门槛：

变量 示例值 长度 校验门槛 结果
JWT_SECRET change-me-to-a-long-random-secret 32 字符 JwtAuthFilter 要求 ≥32 字节 ✅ 通过
INITIAL_ADMIN_PASSWORD change-me-before-first-start 28 字符 DataInitializer 要求 ≥12 字符 ✅ 通过
AETHERIS_INTERNAL_TOKEN change-me-internal-token 26 字符 仅要求非空 ✅ 通过

docker-compose.yml 用的是 ${JWT_SECRET:?} 语法——它只校验"变量已设置"，不校验"值不是示例值"。

影响：按 README 的"cp .env.example .env → docker compose up"照做的用户，会得到一个 JWT 密钥公开在 GitHub 上的、管理员口令可猜的 可运行系统。攻击者可以离线伪造任意用户的 JWT（包括 admin），而 AETHERIS_INTERNAL_TOKEN 泄露意味着服务间身份签名（X-Aetheris-Identity）可被伪造。

修法（详见 D3）：
1. .env.example 的敏感项留空，附带生成命令；
2. 启动时校验"值不等于示例值"，命中即拒绝启动并打印明确错误；
3. 提供一个 make secret / 引导脚本，一键生成全部随机密钥；
4. 顺带统一镜像标签：.env.example:22 是 m1-exec-base-20260908，docker-compose.yml:69 默认是 security-20260908——不一致会导致拉错镜像。

5. 高危问题详解（H1–H7）

H1. 权限逐行远程鉴权：一次列表请求 = N 次 HTTP

证据 services/metadata/.../controller/MetadataTableController.java:69 与 :189-195：

case OPAQUE -> filteredList(request, service.list());   // ← 先把全表捞出来
...
return tables.stream()
    .filter(table -> security.isAllowed(username, "table", table.getId(), "view", ...))
    .toList();                                          // ← 每张表一次远程鉴权

MetadataSecurity.isAllowed → AuthPermissionClient → POST /internal/permissions/check，每条记录一个往返。同样的写法在 SemanticMetricController.java:37-43 也存在。

影响：OPAQUE 模式下（用户没有任何 manifest 级授权时），一个 200 张表的列表页 = 200 次跨服务 HTTP。而 AuthPermissionGate 的超时配置是 500ms 连接 + 1500ms 读（apps/gateway/.../AuthPermissionGate.java:38-40）——auth 一旦抖动，单次请求最坏 200 × 2s = 400s，页面直接挂死，并且形成对 auth 的自我 DDoS。这是本次审视中"改动收益最大"的一条。

修法：
1. 用 visibility 接口一次性取回可见 ID 集合，SQL 用 IN (...) 过滤，把 N 次网络调用压成 1 次；
2. 单请求内对 (user, resource, id, action) 做 request-scope 本地缓存，去重重复判定；
3. 给"逐行判定"设硬上限（超过阈值直接拒绝并要求走授权），避免无界放大。

H2. 血缘影响分析：每跳全表加载，最坏 500 次

证据 services/metadata/.../service/FieldLineageService.java:37（单行压缩写法）：

public List<LineageFieldRelation> impact(String table,String column){
  ...
  while(!queue.isEmpty()&&seen.size()<500){
    String key=queue.removeFirst();
    List<LineageFieldRelation> next=list(null,null).stream()      // ← list(null,null) = 全表加载
        .filter(r->r.getSourceTable().equalsIgnoreCase(parts[0])
                 && r.getSourceColumn().equalsIgnoreCase(parts[1])).toList();

list(null, null) 每次迭代都把整张 lineage_field_relation 拉进内存再内存过滤。循环上限 500，最坏情况 = 500 次全表扫描 + 500 个临时 List。

影响：血缘图是"数据资产识别最后一公里"的核心能力（也正是你近期商业化的方向），但它在真实规模下会先超时或 OOM。表越全、血缘越密，越容易崩——这是一个会随成功而恶化的缺陷。

修法：按 (source_table, source_column) 建索引，把逐跳查询改成带 WHERE 的递归 CTE（PostgreSQL WITH RECURSIVE），一次数据库往返拿到全链路；或在应用层做逐跳 WHERE source_table IN (...) 的批量查询，并把 seen 上限做成可配置的保护阈值而非性能依赖。

H3. 语义指标列表 N+1 + 无 LIMIT

证据 services/metadata/.../service/MetricDefinitionService.java:79-89（列表路径）与 :280-294（resolvePublished）：

mapper.selectList(...).stream().map(this::resolvePublished)...
// resolvePublished 内部再各查一次：版本快照(jdbc.query) + 业务域(domainService.require)

同一个文件 :81-88 还显示先全量捞出再在内存里过滤 keyword/domain，没有 LIMIT。

影响：列表接口的查询次数 = 指标数 × 3，且结果集随指标增长无界。语义层是这个平台对外最有价值的能力（README 花了整整一节讲它），它的入口接口却是 N+1 + 无界。

修法：快照表与业务域 JOIN 一次取回；keyword/domain 过滤下推 SQL；分页参数强制上限。

H4. @Transactional 事务内发起远程 HTTP 调用

证据 services/workflow/.../controller/TaskController.java:117,121 与 :158：

@PostMapping
@Transactional                                    // ← 事务已开启
public ResponseEntity<?> create(@Valid @RequestBody Task task, ...) {
    String rejection = validateDefinition(task);  // ← 内部走 POST /internal/sql/validate-write

validateDefinition → executionClient.validateWrite(...) 是跨服务 HTTP。

影响：事务横跨网络 I/O。metadata 变慢或超时时，数据库连接被长时间占用（持有连接的线程在等网络），连接池（AETHERIS_DB_POOL_MAX_SIZE 默认 8，见 docker-compose.yml:18）很容易被耗光，进而整个 workflow 服务失去数据库连接。这是典型的"小改动、大风险"。

修法：把远程校验移到事务边界之前（Controller 先校验，再进事务方法），事务内只做本地持久化。改动量极小。

H5. 看板发布版本号非原子 → 并发必现 500

证据 services/serving/.../repository/AnalyticsRepository.java:116-132：

int version = dashboard.publishedVersion() + 1;                    // ← 先读
jdbc.update("INSERT INTO serving.bi_dashboard_version(...) ...");   // ← 后写

唯一约束见 services/serving/src/main/resources/db/migration/V1__analytics.sql:51 的 UNIQUE(dashboard_id, version_no)。

影响：两个管理员（或两次重试）同时发布，都算出同一个 version，插入撞唯一约束抛 DuplicateKeyException。而 serving 恰好是 8 个没有全局异常处理器的服务之一（H7）——用户看到的是裸 500，没有"版本冲突，请刷新重试"的提示。

修法：改成单语句原子递增（version_no = (SELECT COALESCE(MAX(version_no),0)+1 FROM ... WHERE dashboard_id=?)，或 INSERT ... ON CONFLICT），并把 DuplicateKeyException 映射为 409 Conflict。

H6. 质量规则表达式弱校验后直接拼 SQL

证据 services/quality/.../service/QualityExecutionService.java:92-108：

return "SELECT COUNT(*) AS violation_count FROM " + target + " WHERE NOT (" + expression + ")";

而"安全校验"只有 :120-125 这一层：

private void rejectUnsafeExpression(String expression) {
    if (expression.contains(";") || upper.contains("--")
        || upper.contains("/*") || upper.contains("*/")) {
        throw new IllegalArgumentException("规则表达式只允许单条语句且不能包含注释");
    }
}

影响：只拦分号与注释，子查询、函数调用、布尔恒等式全部放行。例如 NOT (1=0 OR (SELECT pg_sleep(30))::text <> '') 之类可以构造慢查询绕过"只读"语义。target 有 requireQualifiedIdentifier 保护（[A-Za-z_][A-Za-z0-9_$]* 的 1–3 段），但 expression 没有。

缓解因素：规则需要 quality 的写权限才能配置，因此不是未授权攻击面，而是"有配置权的用户可越过预期的只读约束"。定性为高危而非阻断。

修法：复用 SemanticMetricQueryService 的思路——表达式走白名单 AST 解析（列名 + 允许的操作符 + 字面量），而不是字符黑名单；sql 类型分支同理，^(SELECT|WITH) 这个正则太弱。

H7. 8/10 服务没有全局异常处理器

证据：

grep -rl ControllerAdvice services/*/src  → 仅 auth、metadata
各服务统计：auth 1 / metadata 1 / system 0 / quality 0 / ingestion 0
           governance 0 / workflow 0 / ai-agent 0 / serving 0 / gateway 0

影响：这 8 个服务的任何未捕获异常直接把异常消息和堆栈返回给调用方，同时暴露内部类名/路径信息（信息泄露），并让前端只能靠 message 字符串猜错因。H5 的"裸 500"就是这个缺陷的直接表现。这是一条低成本、高一致性收益的修复。

修法：抽一个共享的 @RestControllerAdvice 基类（或者各服务 15 行统一实现），把异常映射成统一错误体：{code, message, requestId}；DuplicateKeyException → 409、AccessDenied → 403、MethodArgumentNotValid → 400、其余 → 500 且只回 requestId 不回堆栈。

10. 一条逆耳的提醒（战略层）

代码层面我挑出了 26 个问题，但最大的风险不在代码里。

这个项目现在的状态是：5.4 万行手写代码、442 个全绿测试、11 个健康容器、56 个整齐的迁移、10 个微服务的完整闭环——工程密度在国内个人项目里属于极罕见的一档。但同时：

  • 没有一次备份；
  • 没有一个指标端点；
  • 没有一条跨服务 traceId；
  • 没有一个能被别人按文档安装起来的发布物；
  • 语义层最强的能力（跨表 JOIN、派生指标）仍在"已知边界"里没做；
  • 而 docs/roadmap.md 里 M5b 这样的供应链细节已经做到了"过度精密"的程度。

这说明过去一段时间的投入分配，偏向"证明我能做难的事"，而不是"让别人能用起来"。 对"1–2 个月内产生现金流"这个目标来说，前者的边际收益正在快速下降。

结合你正在考虑的"数据资产识别最后一公里"定位（记为 H2），我的判断是：

  1. 能力上你已经够了——元数据、血缘（表级 + 字段级）、业务域、语义指标、质量、权限、审计，"数据资产识别"需要的零件基本齐全。缺的不是功能，是规模化下的性能（H2/H3 就是直接拦路的两个）和可交付性（B1/B2/B3）。
  2. 所以本周这 7 天不是"技术债清偿"，而是"把资产变成可变现形态"的必要前置——一个连备份都没有、慢查询查不到原因的系统，无论定位多好，都过不了任何一个客户的采购技术评审。
  3. 下周之后的方向取舍，建议在 D7 明确写成文档：是继续推进 R1 实时湖仓（12–20 个月的 GA 长路），还是先做"数据资产识别"的最小可交付版本（安装包 + 资产盘点报告 + 血缘影响分析），用 1–2 个月验证能否换回现金流。 这两条路的排期不冲突，但资源的先后顺序必须现在定，否则会继续"哪儿难做哪儿"。
