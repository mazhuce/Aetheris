# Aetheris 企业级交付路线图

> 基线日期：2026-09-12
> 目标：从“核心链路可运行的数据平台”推进到“可以交付给外部客户安装、升级、运维并承担生产责任的企业产品”。
> 本路线图与 `docs/roadmap.md` 分工：后者记录已经完成的产品能力，本文件定义后续交付顺序、验收门槛和停止项。

## 1. 结论

Aetheris 已经具备较强的批处理开发、可靠调度、语义指标、基础治理、数据看板和智能问数能力，尤其 M1–M5b 在执行审计、故障状态、Git 修订固定和供应链证据方面已经超过普通原型。

当前主要缺口不再是“再补几个管理页面”，而是四类生产闭环：

1. **实时数据面**：Flink CDC、流任务状态恢复、Schema 演进、事件时间和实时质量已经形成控制面代码与阶段性运行证据，完整 CDC 增量、重启和线上 soak 仍未完成。
2. **湖仓控制面**：目录、表生命周期、快照、维护计划和跨引擎兼容控制面已经落地；R5 已在隔离真实 Runner + REST Catalog + MinIO 上完成维护动作、对象存储结果回写和清理验收，持续并发恢复演练仍是后续工作。
3. **可信消费面**：智能体缺少权限感知检索、引用溯源和持续评测；看板缺少联动、钻取、共享、订阅、告警和规模化查询能力。
4. **对外交付面**：安装、升级、回滚、身份集成、租户隔离、可观测、备份灾备、容量基准和客户支持体系尚未完成。

从当前状态到首个可对外交付版本，建议再做 **14 次大迭代**。其中前 11 次完成产品，后 3 次只做生产验证、试点和收敛，不再扩功能。

- **企业 Beta（可在受控客户环境试用）**：完成 R1–R10，约 10 次大迭代。
- **企业 GA（可承诺安装、升级、恢复和支持）**：完成 R1–R14，约 14 次大迭代。
- 若每次大迭代按 2–3 周计算，3–5 人稳定团队约需 8–12 个月；单人主导并使用 AI 辅助，现实估计为 12–20 个月。时间取决于目标数据库、云对象存储、身份系统和客户现场环境数量。

## 2. 目标架构

```text
业务数据库 / 消息流 / 文件
       │
       ├── Flink CDC / Flink SQL ── checkpoint、savepoint、HA、Schema 策略
       │                 │
       │                 └── 可选 Kafka 缓冲与多消费者分发
       │
       ▼
Iceberg v2 湖仓表（对象存储 + REST Catalog）
       │
       ├── Flink：持续写入、实时聚合
       ├── Spark：批处理、历史回填、重算、表维护
       └── Trino：交互式查询候选引擎
                         │
                   Aetheris 查询网关
                         │
              语义层 / 权限 / 审计 / 限额
                 ┌───────┴────────┐
                 ▼                ▼
              数据看板         数据智能体
```

### 2.1 必须坚持的边界

- Aetheris 继续作为**控制平面**：管理元数据、权限、语义、任务定义、发布、审计和运行状态，不自行重写 Flink、Iceberg 或查询引擎。
- Flink 是**持续计算引擎**，不是面向用户的查询接口；看板和智能体不得直接读取 Flink 作业状态或绕过查询网关。
- Iceberg 是统一湖仓表格式；首期只支持 format v2，不同时引入 Delta、Hudi、Paimon 等第二套表格式。
- Spark 保留批处理、回填和维护职责，不继续把 Spark Thrift 扩展成所有交互查询的唯一入口。
- Trino 先通过基准验证后再成为湖仓交互查询引擎；若真实 P95 和并发不优于现有路径，则不强行引入。
- 开发环境可使用本地 S3 兼容对象存储；生产必须支持客户自有 S3、OSS、COS、Ceph 等外部对象存储，不把本地 HDFS 固化为唯一生产方案。
- REST Catalog 作为目录接口边界，具体实现通过兼容性验证后确定，避免业务代码绑定单一厂商。

### 2.2 版本策略

Flink CDC、Flink 和 Iceberg 的发布节奏并不完全同步，因此不追“每个组件都用最新”。R1 必须先生成并锁定一份 BOM：JDK、Flink、Flink CDC、Iceberg runtime、Spark、Trino、对象存储 SDK 和各数据库驱动逐项做兼容测试。

历史候选曾考虑 **Flink 2.2 + Flink CDC 3.6**，但本项目 R1 已选择并锁定可复现组合：**JDK 17.0.15 + Flink 1.20.1 + Flink CDC 3.4.0 + Iceberg 1.7.1 + Spark 3.5.6 + Trino 476**，具体以 `configs/lakehouse/r1-bom.toml` 为准。R1 的 Flink → Iceberg v2 → Spark/Trino 写读与空环境重建已通过，BOM 已晋级 approved；PostgreSQL/MySQL CDC、重启恢复和完整 R2 运行态已在隔离 Compose 通过独立验收，不回写或漂移 R1 版本组合。所有 connector JAR 必须有来源、许可证、摘要和漏洞扫描记录。

数据源 JDBC 驱动也属于可复现交付范围：PostgreSQL、MySQL、SQL Server、Oracle、ClickHouse、SQLite、Hive 和 Trino 的版本、Maven Central URL、SHA-256、许可证及许可证链接已纳入同一 allowlist；release gate 会拒绝 BOM 与驱动坐标漂移，避免仅在前端目录中宣称支持。

## 4. 数据智能体扩展清单

### P0：先让回答可信

- **权限贯穿**：用户身份、租户、workspace、数据范围和字段策略必须进入检索与每次工具调用，不能只保护聊天记录。
- **逐项引用**：回答中的指标值可展开查看指标编码/版本、数据集、SQL 哈希、执行 ID、Iceberg snapshot ID、数据时间和更新时间。
- **评测平台**：按客户业务建立问题、期望口径、允许误差、禁止数据和对抗提示；每次模型、提示词、工具和语义版本变更自动回归。
- **结果验证**：先查已发布指标，再查语义模型，最后才允许生成只读 SQL；SQL 执行前做 AST、权限和成本校验，执行后做空值、单位、时间范围和异常量级检查。
- **成本与稳定性**：记录模型、token、延迟、失败分类和每租户预算；支持超时、重试、熔断、模型降级和缓存，但缓存也必须带权限版本。

### P1：再让智能体真正有用

- 基于指标树做贡献度、环比、同比和异常归因。
- 结合血缘、质量规则和任务日志解释“为什么今天少了数据”。
- 生成 SQL、质量规则、指标和看板**草稿**，展示 diff，审批后才发布。
- 把实时质量告警、Flink lag、checkpoint 失败和业务指标异常汇总为事件，并给出证据链和处置建议。
- 在既有看板中生成自然语言摘要，但摘要必须绑定看板版本和查询快照。

### 暂缓

- 暂不建设自由组合的“多 Agent 市场”。当前最重要的是单一数据智能体的正确率、权限和可审计性。
- 暂不允许智能体自主执行删表、授权、发布、生产重跑、Schema 变更等高风险动作。
- 暂不追求模型数量；一个主模型、一个降级模型和可复现评测，比接十个模型更有交付价值。

## 5. 数据看板扩展清单

### P0：企业分析必需

- 页面级全局筛选、时间范围、参数和筛选联动。
- 图表点击联动、下钻/上卷、明细穿透、同比/环比和目标线。
- 看板发布审批、不可变版本、回滚和变更说明。
- 看板/组件/数据集三级权限校验，行列策略延续到查询、缓存、导出和订阅。
- PDF/Excel/图片导出，邮件/Webhook 订阅，指标阈值与数据新鲜度告警。
- 实时看板使用 SSE/WebSocket 或受控增量刷新；浏览器不可直接连 Flink/Kafka。
- 查询取消、超时、并发控制、缓存、预聚合和大结果分页。

### P1：增强体验

- 散点、漏斗、地理、热力、双轴等少量高价值图表；不以图表数量作为成熟度指标。
- 注释、事件标记、业务日历、全屏电视模式和移动端只读布局。
- 模板从“静态样式”升级为绑定语义角色的可复用分析模板。
- 看板使用热度、慢组件、失败率、订阅送达率和废弃建议。

## 6. 之前投入中应停止继续加码的部分

这些工作并非没有意义，而是相对当前短板已经出现边际收益下降：

1. **继续反复做整体视觉翻新**：当前中性企业设计已足够进入试点。后续只修真实可用性问题，视觉重构应由客户研究和可用性测试触发。
2. **为 `comingSoon` 菜单补占位 CRUD**：页面数量不会提高交付成熟度。没有真实执行、权限、失败恢复、审计和测试的功能继续隐藏。
3. **继续扩展 M5b 供应链细枝末节**：Git commit/blob/签名/Runner 摘要闭环已经很强，应封板维护。现阶段备份、身份、安装升级和实时恢复的优先级更高。
4. **把本地 HDFS + Spark Thrift 当成最终生产架构**：它是有价值的兼容与开发验证环境，但不应继续承担统一湖仓控制面和高并发交互查询职责。
5. **堆更多图表类型和漂亮模板**：在全局筛选、权限、分享、订阅、缓存和性能未完成前，新增大量图表的客户价值有限。
6. **过早建设通用 Agent 编排平台**：没有评测、引用、权限和审批的多 Agent 只会扩大风险与维护面。
7. **每次小修改都完整重打所有容器**：日常开发应使用受影响模块测试；只有集成候选和正式发布才做全量构建、镜像签名、迁移和恢复演练。

## 8. 每次迭代统一完成标准

任一能力只有同时满足以下条件才能从“规划/可用”升级为“完整/企业级”：

1. 使用真实数据和真实执行器，不以模拟响应或静态页面验收。
2. 数据库迁移可重复执行；涉及升级风险时有回滚或前向修复方案。
3. 服务端完成身份、租户、资源和数据范围校验，不能依赖前端隐藏按钮。
4. 密钥、凭据、SQL 参数、日志和错误响应经过安全审查与脱敏。
5. 单元、契约、集成和关键 E2E 自动化通过；状态型能力补故障注入和恢复测试。
6. 有容量目标并记录 P50/P95/P99、吞吐、资源占用和退化行为。
7. 有审计、指标、日志、trace、告警和可执行 runbook。
8. Compose 升级验证通过；R12 后同时要求 Kubernetes 升级/回滚验证。
9. 用户、管理员和运维文档同步；界面明确显示失败、部分成功、未知和可恢复状态。
10. 不删除或覆盖用户未纳入本次范围的文件与改动；提交保持单一主题、可回滚。

## 9. 当前迭代出口与下一步

R1 的第一条硬门槛“跨引擎读写一致且可重建”已经有历史运行证据、固定 BOM、connector SHA-256 校验和一键验收脚本；当前环境恢复后必须重新执行脚本确认部署级结果不漂移。

下一步按 R2/R3 推进：

1. 在真实隔离环境完成 PostgreSQL/MySQL CDC 的全量快照、UPDATE/DELETE/INSERT、checkpoint、TaskManager 重启和最终一致性对账。
2. 将 JobManager 的 Job ID、checkpoint、savepoint、stop-with-savepoint 和失联对账接入实际 Flink 任务，并完成服务重启后的恢复演练。
3. 将 Spark 制品上传、Flink 生命周期、CDC 状态和失败证据接入前端工作台，而不是只保留 API。
4. 之后进入 R4/R5 的线上验证：Schema 演进审批、迟到/死信、Gold 阻断、快照维护、回滚和成本统计。
